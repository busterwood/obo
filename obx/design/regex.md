# A regex engine for obx

Status: R1 built, 2026-11-03 (branch `r1`; "R1 as built" in section 3);
R2 built, 2026-11-03 (branch `r2`; "R2 as built" in section 3).
R2 and R3 are plans. No language change was needed.

## 0. Goal and choice

`import "regex"` gives regular expressions that are safe on any input:
matching time is linear in the input's length, whatever the pattern. This
is the RE2 family, which Go's `regexp` and Rust's `regex` both belong to:
no backreferences and no lookaround, which are the features that make
backtracking engines exponential.

The design is Go's, ported: a parser, a compiler to a small instruction
program, and three matchers chosen per pattern and input. On top of it come
Rust's two biggest wins, a literal prefilter and a lazy DFA (R2). Rust's
whole engine (about 50,000 lines with its SIMD and special cases) is too big
to port faithfully. Go's (about 6,000) can be ported and checked line by
line against its tests.

Needed for the tools on the roadmap: fd matches filenames with a regex by
default, and jq has `test`, `match` and `sub`. jq's own engine
(Oniguruma) has backreferences and lookaround, so jq programs that use them
will not run.

Licences: Go is BSD-3-Clause and Rust's regex is MIT or Apache-2.0, both
compatible with obx's Apache-2.0. Ported code keeps a header naming its
origin, and `NOTICE` carries their copyright lines.

## 1. Syntax

RE2's syntax, as in Go:
- literals and escapes;
- `.`, `[...]`, `[^...]` and `[[:alpha:]]`;
- `\d \w \s` and their negations;
- `\pL \pN` (R1), and `\p{Greek}` and the other scripts (R3);
- `* + ? {n,m}` and their lazy forms;
- `|`, `(...)`, `(?:...)` and `(?P<name>...)` / `(?<name>...)`;
- flags `(?i)`, `(?m)`, `(?s)` and `(?U)`;
- `^ $ \A \z \b \B`.

Patterns and text are UTF-8 strings, matched by code point. An invalid
UTF-8 byte in the text matches only `.` and negated classes, as in Go.

Refused with a clear error: backreferences (`\1`), lookaround (`(?=`,
`(?!`, `(?<=`, `(?<!`), possessive quantifiers, a repetition count above
1000, and a program larger than a fixed limit (as in Go, so a pattern
cannot exhaust memory).

## 2. API

```obx
import "regex"

let re = try regex.compile("(?P<y>\\d{4})-(?P<m>\\d{2})-(?P<d>\\d{2})")
if re.isMatch("on 2026-11-03") { ... }
match re.find(text) { Some(m) { m.start; m.end; m.text } None {} }
for m in re.findAll(text) { ... }
match re.captures(text) {
    Some(c) { let y = c.name("y").unwrap().text }
    None {}
}
let s = re.replaceAll(text, "$d/$m/$y")
let parts = re.split(text)
```

- `compile` returns `Result[Regex, regex.Error]`. The error carries the
  position and the reason. `regex.mustCompile` is for constants.
- `Regex` is immutable once compiled, and a copy handle shares the program.
  The matching state (thread lists, the backtracker's bitmap, later the DFA
  cache) is per call or kept in a small per-`Regex` cache. With tasks on
  one thread nothing is shared across threads, so no locks are needed.
- Offsets are byte offsets into the string, as in Go and Rust.
- `regex.quote(s)` escapes a literal.

## 3. Phases

### R1: Go's engine

| Part | Go source | Notes |
|---|---|---|
| parser and syntax tree | `regexp/syntax/parse.go` | the flags, classes, names and limits in section 1 |
| simplification | `simplify.go` | `x{2,5}` expanded, and so on |
| compiler to a program | `compile.go`, `prog.go` | the instructions: rune, rune ranges, any, empty-width assertions, split, capture, match |
| backtracker | `backtrack.go` | for small programs times small inputs, with a visited bitmap, so still linear |
| one-pass matcher | `onepass.go` | for patterns where every step has one choice: captures in one pass |
| Pike VM | `exec.go` | the general case: an NFA simulation with captures |
| API | `regexp.go` | `find`, `findAll`, `captures`, `replace`, `split` and their index forms |

Unicode in R1: `\pL`, `\pN`, `\pZ` and the other general categories, with
simple case folding for `(?i)`. The tables are generated by a Python script
from the Unicode data file that Go's tables come from. Scripts and full
case folding are R3.

Tests:
- Go's test tables ported as obx tests: `find_test.go`, `all_test.go`, the
  `re2-search.txt` exhaustive cases, and the parse and error tests. Every
  expected result is compared with Go's.
- A random generator, as `vrgen.py` is for the compiler: patterns and
  texts, with the results compared against Go's `regexp`, which is
  installed here, by a small Go driver program.
- Hostile patterns stay linear: `(a*)*b` and `(x+x+)+y` over long inputs,
  with the time bounded.

Gate:
- Go's tests pass and the generator finds no difference;
- no leaks under `OBX_CHECK=1`, ASan and UBSan, on both backends;
- speed within a small factor of Go's `regexp` on the benchmark set
  (section 4), natively.

### R1 as built

Branch `r1`, 3 November 2026. About 4,700 lines of obx plus 2,000 lines of
generated tables, in three modules (one per Go package):

| Module | Go source | Contents |
|---|---|---|
| `lib/regex_unicode.obx` | `unicode/tables.go` | generated by `lib/gen_regex_unicode.py`: Unicode 15.0.0, 201 classes (38 general categories and 163 scripts) in 8,602 range pairs, their fold tables, 42 category aliases, 2,878 simple case-folding pairs |
| `lib/regex_syntax.obx` | `regexp/syntax` | the parser with Go's errors and limits, the tree (an arena of value nodes, `Tree.nodes`), `String`, simplify, the compiler to a `Prog`, its dump, literal prefix and start conditions |
| `lib/regex.obx` | `regexp` | the one-pass matcher, the bounded backtracker, the Pike VM and the API |

The API is section 2's, with Go's index forms, `findN`, `capturesAll`,
`replace` (the first match), `replaceN`, `replaceAllLiteral`,
`replaceAllFunc`, `expand`, `splitN`, `compileLongest` and
`compilePosix` (lib/README.md lists them). Results are named records:
`Match {start, end, text}`, `Span {start, end}`, `Captures`, `Prefix {text,
complete}`.

**Matcher selection** is Go's, per search: no match if the text is shorter
than the pattern's minimum length; the one-pass matcher if the program is
one-pass (anchored at the start, each step one choice); else the bounded
backtracker if the program has at most 500 instructions and the text is
shorter than 256 Kbit / instructions; else the Pike VM. The backtracker
and the Pike VM first look for the literal prefix, if any.
`matcherFor(n)` says which a text of n bytes gets.

**Tests** (expected values are Go's, generated by running Go's own tests;
`tests/regex/gen_go_tests.py` regenerates them):
- `regex_parse`: 588 parse dumps and errors (Go's parse, fold-case,
  literal, match-NL, invalid, Perl-only and POSIX-only tables), `String`,
  simplify and program dumps;
- `regex_find`: find_test.go's 87 cases through every API form,
  leftmost-first and leftmost-longest, under the matcher compile picks and
  with the Pike VM and the backtracker forced;
- `regex_api`: compile errors (Go's exact messages), replace (literal,
  template, function), quote, literal prefix, group names, split,
  one-pass detection and minimum length;
- `regex_re2search`: re2-search.txt's 1,888 cases, four modes (full and
  partial, both semantics) under three matchers: 21,648 runs;
- `regex_linear`: five patterns that are exponential for a backtracking
  engine, linear here;
- `tests/regex/re2_exhaustive.py` (opt-in, as in Go): the 5.7 million cases
  of re2-exhaustive.txt.bz2, 62 million runs, no failure (natively 43 s);
- `tests/regexgen.py`: random patterns and texts against Go's `regexp`
  through a Go driver: compile errors, all submatch indexes in both
  semantics, `replaceAll` and `split`, and the three matchers against each
  other. `gate.sh full` runs its fast mode (400 patterns, both backends,
  3 s); seeds 1 to 5 and 11 to 13, up to 3,000 patterns and texts of up
  to 3,000 bytes, found no difference.

**Speed**: PERFORMANCE.md, section Regex. Through C, obx is level with Go
on the Pike VM patterns and up to 1.45 times its time on the others;
natively 2 to 3 times Go's time at R1, which was the native backend's code
for the Pike VM's loops (the same code ran twice as fast through gcc). The
eighth native performance step (branch `perf8`) brought that to 1.4 to 2.3
times Go's time, and 1.4 to 1.8 times the gcc build's cycles.

**Deviations from the plan and from Go:**
- Scripts (`\p{Greek}`, Go's `unicode.Scripts` with their fold tables) are
  in R1, not R3: they are table data only, and re2-search.txt uses them.
  Blocks and full case folding remain R3.
- The tables are generated from Go's `tables.go`, which is generated from
  the Unicode data files, rather than from the data files themselves: the
  classes and folds are Go's by construction, and no download is needed.
- `Regex` is an owned record, used through `&Regex`; it is not a copy
  handle that shares the program (obx has no shared immutable handle
  without a language change). Matching state is per call (an `Exec`
  record kept across the matches of one `findAll`), not a cache in the
  `Regex`, which stays immutable.
- `Error` carries the byte offset of the offending part (`pos`) besides
  Go's code and text; `message()` is Go's text, `toStr()` adds a hint for
  backreferences, lookaround and possessive repeats.
- `findAll` and the like return arrays (no iterators yet).
- Not ported: Go's Fowler tests (`testdata/*.dat`, POSIX semantics), the
  internal rune-merging tests of onepass_test.go, and Go's
  `MarshalText`/`Longest()` mutation (use `compileLongest`).
- `\B` follows Go (positions between runes), not RE2 (every byte); Go's
  re2-search runner skips the 4 cases where they differ, and so does ours.

### R2: Rust's wins

- **Literal prefilter.** From the syntax tree, find the literal prefix, or
  the literals one of which every match must contain. The search then
  jumps to them with a fast memory search: `memchr`, or a word-at-a-time
  `memmem`, in the runtime; Aho-Corasick for a few literals. For most real
  patterns this is where ripgrep's speed comes from.
- **Lazy DFA** (RE2's and Rust's "hybrid"): DFA states are built from the
  program while matching, in a cache of fixed size. A search runs forward
  to find where the match ends, then backward with the reversed program to
  find where it starts. Only when captures are asked for does the Pike VM
  (or the one-pass matcher) run on that span. If the cache fills too often,
  the search falls back to the Pike VM.

Gate: within a small factor of Rust's `regex` on the benchmark set, and the
tests and the generator still agree with Go.

### R2 as built

Branch `r2`, 3 November 2026. About 1,250 lines of obx in a new module,
`lib/regex_dfa.obx`, 300 in `lib/regex.obx`, 50 in `lib/regex_syntax.obx`,
and four memory-search intrinsics in both runtimes.

**Memory search** (`compiler/rt.h`, `compiler/native/rt.c`; SSE2, 16 bytes
a step, with a byte loop elsewhere): `strFindByte` (memchr), `strFindAny`
(the first byte of a set of up to 16 bytes, by comparisons), `strFind`
(memmem as Rust's memchr crate does it: the two rarest bytes of the needle
by a fixed frequency rank, compared at their offsets, a candidate checked
with memcmp) and `strFindPair` (a position p with `s[p+i1]` in one set of
up to 4 bytes and `s[p+i2]` in another). They are intrinsics, as `strByte`
is: the regex code is obx and calls them. Teddy (Rust's SIMD multi-literal
search) was not ported: `strFindPair` on the two rarest positions of a few
literals does the alternation's job, with a byte check for the rest.

**Literal extraction** (after Rust's `regex-syntax` `hir::literal`): from
the tree, a finite set of literals, each exact or a prefix of a match, with
the limits 250 literals, 32 runes, classes of at most 10 runes; `(?i)`
expands to the case orbit (`k`, `K`, the Kelvin sign); U+FFFD has no
literal (it matches every invalid byte). Literals another literal begins
are dropped. The same code run on the reversed tree gives suffix literals,
and on a tail of the top concatenation the "inner" literals. A literal set
becomes a **prefilter**: one literal (`strFind`), two bytes at two offsets
(`strFindPair`, picked as the rarest pair from a byte-frequency table) or a
byte set at an offset (`strFindAny`), with an estimated candidate rate. A
prefilter that is estimated or measured (after 64 uses, if it skips fewer
than 16 bytes a use) to be poor is not used.

**Lazy DFA** (`regex_dfa.obx`, RE2's `dfa.cc`):
- A state is the ordered list of the program's live instructions (rune,
  match, and empty-width tests not yet satisfied), as RE2's; in
  leftmost-longest mode marks separate the threads of different start
  positions and each group is kept sorted. Its flags hold the empty-width
  context (begin of text and line, the last rune a word rune), a delayed
  match, "unanchored: start new threads after each rune" (instead of RE2's
  `.*?` prefix, so the reverse program needs no copy) and "only fresh start
  threads" (where a prefilter may skip ahead).
- **UTF-8 approach**: the DFA steps by rune, not byte. Runes are split
  into equivalence classes (every instruction's ranges, `\n` and the word
  set refine them); an ASCII byte finds its class in a 128-entry table,
  other runes are decoded as Go decodes them (an invalid byte is U+FFFD,
  one byte wide) and found by binary search; one extra class is the end of
  text. Results are Go's by construction (same decoding; `\b`/`\B` between
  runes), and a pattern's classes stay few (a row of the table is a few
  words, not 256).
  The cost is a decode on non-ASCII text, which a byte DFA avoids; the
  benchmark corpus is ASCII.
- Transitions are 64-bit: the next state's row offset, with tag bits for
  "match before this rune", unknown, dead and cache full, so the inner loop
  is one load and one compare for a known non-matching step.
- The cache is 2 MB of transition and state words. When full it is
  cleared (the current state is kept), and a search that has cleared it
  before and since scanned fewer than 10 bytes per state built gives up
  (RE2's rule); the call then finishes with the Pike VM or backtracker.
- Search: the forward DFA finds the end of the leftmost match (the last
  match state before the dead state; the earliest one for `isMatch`), the
  reversed program (`syn.compileReverse`), anchored and leftmost-longest,
  run backward from there finds its start. Captures run the backtracker
  (with a bitmap over the span only) or the Pike VM anchored at the start
  and limited to the span. Patterns anchored with `\A` skip the reverse
  run.
- **Reverse-inner search** (Rust's): when no prefix prefilter is good, a
  literal inside the top concatenation whose first bytes cannot occur in
  the part before it: find the literal, run the reversed part backward to
  the leftmost start, then the whole pattern forward from there. As the part
  cannot contain the literal's first byte, the first candidate that works
  gives the leftmost match. If a forward run would read again what an
  earlier failed one read (quadratic), the plain search takes over.
- **Suffix check**: a single literal every match ends with is searched for
  first (remembered across a `findAll`): no literal, no match.

**Matcher selection** per search: the one-pass matcher as before; a
literal pattern (Go's complete literal prefix, no conditions) is a
`strFind`; the DFA on texts of at least 128 bytes (measured: below that
Go's matchers start faster; the DFA wins from 32 to 64 bytes on most
patterns but loses on alternations); else Go's choice. `matcherFor(n)`
answers `onepass`, `literal`, `dfa`, `backtrack` or `pike`;
`literalSearch()` `prefix`, `inner`, `suffix` or `none`.
`compileForcing` adds `dfa` (always the DFA, no literal searches),
`prefilter` (every literal search, however poor) and `dfatiny` (a cache of
about three states, cleared at almost every step, never giving up).

**Tests**:
- `regex_find`, `regex_re2search` (now 43,296 runs) and `regex_api`
  (replace, split, quote) also run with `dfa`, `prefilter` and `dfatiny`
  forced; `regex_parse` has no searches;
- `regex_linear` adds the DFA modes and `(a|b)*a(a|b){20}` (2^21 DFA
  states);
- the new `regex_dfa`: five patterns with exponentially many DFA states on
  random text (Pike's matches, linear time), the tiny cache against the
  Pike VM, the literal search chosen for each benchmark pattern, invalid
  UTF-8 and searches starting inside a rune under every DFA mode;
- `tests/regexgen.py` compares the three DFA modes with compile's choice
  too (all submatch indexes in both semantics, and `isMatch`): seeds 1 to 5
  at 3,000 patterns and texts of up to 3,000 bytes (C) and 1,500 patterns
  up to 2,000 bytes (native): no difference;
- `re2_exhaustive.py`: 5,716,884 cases, 124,871,232 runs under six
  matchers (submatch indexes, `isMatch` and `findIndex`), no failure (C,
  2 to 3 minutes).

**Numbers**: PERFORMANCE.md, section Regex. Through C, 1.3 to 2.6 times Rust's
`regex` crate on the benchmark set (email 1.3, `(?i)` 1.8, the alternation
and `\w+` 2.2, the literal and the captures 2.6) and half its time on the
`ERROR` lines; natively 2.0 to 4.0 times. Against R1 (Go's engine), 2 to
650 times faster through C. The gaps that remain are the per-match costs
of `\w+` and the captures, AVX2 on the literal, and the native backend's
checks in the DFA loop.

**A finding: the closure's order.** RE2's DFA keeps, for an empty-width
test that cannot be decided yet (`\b`, `$` need the next rune), the test
alone, and re-adds it when the next rune is known. Go's Pike VM decides
the test at once, and the instructions on the way to it are already marked
visited, which can change the priority order: Go compiles a nullable `x*`
as `(x+)?` (golang.org/issue/46123), and `(\b|s)*` on "s" is 0-0 in Go, but
was 0-1 in the DFA. A leftmost-first state with a waiting test now also
records the instructions its closure passed through, in order, and the
closure is redone in that order with them marked, which gives Go's order
exactly. regexgen found it through `split`: captures had hidden it (the
backtracker on the span returned Go's match), so regexgen, re2-search and
`regex_dfa` now also compare the spans alone.

**Deviations:**
- The DFA is rune-based, not byte-based as in RE2 and Rust (above).
- No Teddy and no Aho-Corasick: the alternation uses `strFindPair` on
  two rare positions; patterns with many literals (beyond 250, or long
  ones) get no prefilter and run the DFA alone.
- The DFA's cache lives in the per-call matching state (`Exec`), not in the
  `Regex` (which is immutable behind `&Regex`, and obx has no interior
  mutability or pool to share a cache across calls without a language
  change). A `findAll` reuses its states; separate `isMatch` calls on the
  same `Regex` rebuild theirs, which costs about a microsecond per call on
  short texts and is why the DFA starts at 128 bytes.
- AVX2 is not used (SSE2 only, which every x86-64 has; no runtime
  dispatch). Rust's memchr uses AVX2 where the CPU has it, which is likely
  most of the gap on the literal.

### R3: Unicode, and what tools need

- `\p{Script}` with scripts and blocks, and full case folding for `(?i)`,
  from generated tables.
- A `RegexSet` that matches several patterns in one pass (fd's
  `--exclude`, routing).
- A byte-oriented mode for matching non-UTF-8 bytes (file contents, as in
  ripgrep).

## 4. Benchmark set

`obx/bench/regex/`: a few MB of text (English prose, a source tree's
files, a log file) and these patterns:

| Kind | Example |
|---|---|
| a literal | `Sherlock Holmes` |
| literals in an alternation | `Sherlock\|Holmes\|Watson\|Irene` |
| a class repeated | `\w+` (all matches) |
| case-insensitive | `(?i)sherlock` |
| something like an email | `[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}` |
| anchored lines | `(?m)^ERROR .*timeout$` |
| captures | the date pattern in section 2, every match with its groups |
| a hostile pattern | `(a*)*b` over 100,000 `a`s |

Each pattern is timed against Go's `regexp` and Rust's `regex`, through
small driver programs built here, and against ripgrep as a reference
point. The results go in `PERFORMANCE.md`.
